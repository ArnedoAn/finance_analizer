# Services v2

Processor orchestrates durable inbox → deterministic ignore rules → template parsers → LLM → Firefly. Use repositories only. Persist ingestion before external requests; guard processing with a shared async lock. Retry transient processing errors with persisted attempts/next_attempt_at; exhausted rows remain manually requeueable. Share TTL account/category cache, refresh missing asset and never create assets. Manual and automatic paths use aware dates, Firefly apply_rules and source external IDs. Scheduler jobs are cycle and sender_learning with no per-session fan-out. Keep privacy: unknown apps/SMS sources retain no raw body. See README for full guarantees.

## Alerts (v4, no bot)

There is no push channel and no bot client: services insert rows into `alerts` through `alerts.emit(session, type, *, title, body, ...)` and the app polls `GET /alerts`. `emit` never commits (the caller owns the transaction) and returns None when suppressed. Anti-noise reuses the `notifications` table under the `alert:` key prefix: the same `dedupe_key` (default: the type) is suppressed inside `min_interval_minutes` (default `NOTIFY_MIN_INTERVAL_MINUTES`). Per-item and per-month events must pass a stable `dedupe_key` and, when they must not repeat, a long interval (`alerts.ONCE_MINUTES`); periodic callers (hourly cycle) must pass an interval at least as long as their cadence.

Titles and bodies are Spanish, with full amounts (`alerts.money`) and never raw message text, OTPs or credentials. `Processor._announce` (item status changes: `pending_review` with `suggestions.suggest`, `question`, `duplicate_suspect`, `big_amount`, failed items) is best-effort and must never fail a finance operation. `Processor.alerts()` runs after every cycle: each check (stale pending, phone silence, budgets, key expiry, backup status, month close, `reports.alert_check`, `anomalies.alert_check`, `capture.*` for `capture_gap`) is isolated, logged on failure and never aborts the cycle. Digest preference and grouping of automatic `new_charge` alerts live in `services/digest.py` (`runtime_flags.digest_policy`; the hourly `digest_tick` job decides what is due). Dashboard snapshots (`services/snapshots.py`, one background recomputation per month; automatic triggers only after `snapshots.enable`) and the server error buffer (`core/error_log.py`: sanitized, 300 rows, 30 days; stores nothing until `error_log.install`) are started by the lifespan in `main.py`.

## AI budget, AI review and learning (v4)

Every LLM call is recorded with `ai_budget.record` (table `ai_usage`, per day and kind); only AUTOMATIC jobs ask `ai_budget.allow` first and stop when today's automatic calls pass `runtime_flags.ai_budget.daily_calls` (default 400) or OpenCode Go reports `rolling.percent >= 60` / `weekly.percent >= 70` (`GET .../go/v1/usage`, at most every 15 min, stored in `runtime_flags.ai_go_usage`). Normal message processing and owner-requested tasks only record. `ai_review` proposes a resolution per automatic `needs_review` item (`ai_suggestions`; REDACTED text only; validated against own accounts, Firefly categories and the message) and applies it only through `Processor.review`; amount and annulment proposals are never applied in bulk. `rules.learn_from_correction` turns two consecutive owner corrections of a merchant to the same category into an active `learned` rule and switches a learned rule off when the owner contradicts it; manual rules are never touched. `counterparties` merges Firefly expense/revenue accounts (never asset accounts), writes the map of moved splits before moving, deletes a source only when Firefly shows it empty and can undo for 7 days. Names of people are the data there: only `redact_identifiers` is applied to what the model sees.
