# Services v2

Processor orchestrates durable inbox → deterministic ignore rules → template parsers → LLM → Firefly. Use repositories only. Persist ingestion before external requests; guard processing with a shared async lock. Retry transient processing errors with persisted attempts/next_attempt_at; exhausted rows remain manually requeueable. Share TTL account/category cache, refresh missing asset and never create assets. Manual and automatic paths use aware dates, Firefly apply_rules and source external IDs. Scheduler jobs are cycle and sender_learning with no per-session fan-out. Keep privacy: unknown apps/SMS sources retain no raw body. See README for full guarantees.

## Alerts (v4, no bot)

There is no push channel and no bot client: services insert rows into `alerts` through `alerts.emit(session, type, *, title, body, ...)` and the app polls `GET /alerts`. `emit` never commits (the caller owns the transaction) and returns None when suppressed. Anti-noise reuses the `notifications` table under the `alert:` key prefix: the same `dedupe_key` (default: the type) is suppressed inside `min_interval_minutes` (default `NOTIFY_MIN_INTERVAL_MINUTES`). Per-item and per-month events must pass a stable `dedupe_key` and, when they must not repeat, a long interval (`alerts.ONCE_MINUTES`); periodic callers (hourly cycle) must pass an interval at least as long as their cadence.

Titles and bodies are Spanish, with full amounts (`alerts.money`) and never raw message text, OTPs or credentials. `Processor._announce` (item status changes: `pending_review` with `suggestions.suggest`, `question`, `duplicate_suspect`, `big_amount`, failed items) is best-effort and must never fail a finance operation. `Processor.alerts()` runs after every cycle: each check (stale pending, phone silence, budgets, key expiry, backup status, month close, `reports.alert_check`, `anomalies.alert_check`, `capture.*` for `capture_gap`) is isolated, logged on failure and never aborts the cycle. Digest preference and grouping of automatic `new_charge` alerts live in `services/digest.py` (`runtime_flags.digest_policy`; the hourly `digest_tick` job decides what is due). Dashboard snapshots (`services/snapshots.py`, one background recomputation per month; automatic triggers only after `snapshots.enable`) and the server error buffer (`core/error_log.py`: sanitized, 300 rows, 30 days; stores nothing until `error_log.install`) are started by the lifespan in `main.py`.

## AI budget, AI review and learning (v4)

Every LLM call is recorded with `ai_budget.record` (table `ai_usage`, per day and kind); only AUTOMATIC jobs ask `ai_budget.allow` first and stop when today's automatic calls pass `runtime_flags.ai_budget.daily_calls` (default 400) or OpenCode Go reports `rolling.percent >= 60` / `weekly.percent >= 70` (`GET .../go/v1/usage`, at most every 15 min, stored in `runtime_flags.ai_go_usage`). Normal message processing and owner-requested tasks only record. `ai_review` proposes a resolution per automatic `needs_review` item (`ai_suggestions`; REDACTED text only; validated against own accounts, Firefly categories and the message) and applies it only through `Processor.review`; amount and annulment proposals are never applied in bulk. `rules.learn_from_correction` turns two consecutive owner corrections of a merchant to the same category into an active `learned` rule and switches a learned rule off when the owner contradicts it; manual rules are never touched. `counterparties` merges Firefly expense/revenue accounts (never asset accounts), writes the map of moved splits before moving, deletes a source only when Firefly shows it empty and can undo for 7 days. Names of people are the data there: only `redact_identifiers` is applied to what the model sees.

## Receipts and bills (v4)

`receipts` (photo → `image_clean.sanitize` → `clients/vision.py` → structured result): the image lives only in memory (EXIF/GPS/XMP removed at container level, pixels never decoded; no Pillow on purpose), only the encrypted reading is stored, `ai_budget.record(..., "receipt_vision", auto=False)` (owner task: recorded, never braked). Matching is amount (+ up to 20 % tip), ±2 Bogotá days and a similar merchant; the split goes through `ledger.update` (undoable). `bills` keeps utility bills: e-mails ignored as non-transactions with two bill words are queued by `bills.consider_ignored` (redacted, encrypted text) and read by the `bills_extract` job of `ai_jobs`; `bills.on_item_created` and `bills.after_cycle` settle bills with a payment to the same entity (±1 %, [issue, due + 10 days]), emit `bill_due` alerts and enforce retention. References are stored masked.


## Second opinion, valley queue, events, cards (v4, ServerQuality)

`second_opinion` (kind `second_opinion`, settings in `ai_features`): after each LLM extraction, and a parser one above `min_amount_cop`, `mimo-v2.6-flash` extracts the same REDACTED text; agreement on amount, type, own account and merchant marks the item `verified` (cap `verified_max_amount_cop`, default twice the policy cap), disagreement sends it to review. Automatic and brakable; braked/failed means no verdict and the normal cap. Never queued. `ai_budget.is_peak/defer_until_offpeak` hold the OpenCode Go peak windows (weekdays UTC 01-04 and 06-10, deepseek costs twice); heavy AUTOMATIC jobs go through `ai_jobs` (`enqueue`, `register`, `dispatch`, `run_due` every minute): valley runs now, peak parks them as `waiting_offpeak` according to `ai_budget` `peak_policy` (`ask` one grouped alert, `wait`, `run`); the owner decides with `/ai/jobs/*`. Per-message processing and owner «now» requests are never queued. `ai_events` (trips/events tag proposals), `ai_forgotten` (monthly, `forgotten_subscription`) and `cards` (`own_accounts.statement_day/payment_day`, `card_payment_due`) follow the same rules: redacted text only, alerts through `alerts.emit`, no commits inside helpers except where documented.


## Declined attempts (v4)

A rejected, declined, failed or insufficient-funds message never becomes a movement. One rule, `parsers.common.is_declined(subject + body)` (folded, warning clauses such as «si su pago fue rechazado…» removed, a labelled «Estado: Aprobada» wins), runs in `Processor._ignore_declined` before any parser, LLM or auto-approval (`_extract`, and the retry of already extracted rows in `process`): status `ignored`, template `ignore.declined`, reason `declined`, nothing written to Firefly. `ai_review` turns an `approve` on such an item into `ignore` (at suggestion time and when a stored suggestion is applied). Only the owner's manual approval (`Processor.review(..., "approve")`) or manual entry registers one.

## Placeholder merchants and masked counterparties (v4)

`parsers.common.is_placeholder_merchant` (PENDING, PENDIENTE, N/A, NULL, UNKNOWN, DESCONOCIDO, SIN COMERCIO, COMERCIO, empty or only signs) decides in `Processor._extract`: a placeholder from the parser or the LLM leaves `merchant` empty and the item in `needs_review` with `review_reason = "merchant_unknown"`; `_merchant` (the only `create_account` caller) refuses one, `review` and `ai_review` never accept one as a correction (422 / ignored). `Processor._unmask` is the single place for a counterparty the bank masks (`is_masked_counterparty`: letters + `**` or more per token, like `PAU*** BET***`; `UBER *TRIP` and `PAYU*NETFLIX` are not masks): exactly one known expense/revenue account or `merchants` name that agrees token by token by prefix is reused and the item gets a `masked_counterparty_matched` event; none keeps the canonical masked name; several set `counterparty_ambiguous` (a correction with an ambiguous mask is a 422).
